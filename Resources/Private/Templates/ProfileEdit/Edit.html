Template: ProfileEdit/Edit - the edit plugin. Variables assigned by ProfileEditController.editAction authenticated bool Whether a frontend user is logged in. Always assigned. profile Domain\Model\Profile or NULL The profile of the calling session, NULL when there is none. Always assigned. Assigned only when profile is not NULL: profileName string The name for the heading and the image alternative text, with the shortname fallback already applied by the controller. addresses list of Domain\Model\Address emails list of Domain\Model\Email Both read through the edit repositories, so they include the records the owner has hidden. profileJson string The profile document, as JSON. endpointsJson string One endpoint URL per action, as JSON. requestToken string The hash signed JWT of the request token. labelsJson string Every string the component renders, as JSON. Three states, and the template decides none of them. It branches on the two booleans the controller assigned, in the order "has a profile" then "is logged in", so that "log in first" and "you have no profile yet" are different sentences rather than one vague one. The four data attributes are the whole contract with the component, and all four are required: profileEdit.ts enhances only when it can read a profile, an endpoint map and a non empty token, and otherwise leaves the markup below alone. They are rendered with plain {variable} interpolation, and that is load bearing: Fluid escapes it with htmlspecialchars, which is what turns the structural quotes of the JSON document into " and makes the attribute well formed. Do not "fix" this with f:format.raw - the first double quote of the document would then end the attribute. The server rendered profile sits INSIDE the element. That is the view a visitor keeps when the module fails to load, when custom elements are unsupported or when an attribute is malformed - the element is an unknown tag with children then, and nothing else. Once it upgrades, it renders its own surface into its shadow root and does not slot these children, so they disappear rather than duplicating what the component draws. Everything the component edits belongs inside, and everything it edits is inside: the name heading, the details, both collections and the image. A value left outside would still show what the page was loaded with after the first save, while the surface next to it showed the new one - the page would disagree with itself about the same record. The image was outside while it was read only. It moved in when the upload and remove endpoints landed, and the detail view still renders it outside its own markup, which is why the two templates place the same partial differently. Profile/Card is deliberately not used here although it renders the image and the name together. That pairing is what the detail view wants; this template composes the two partials itself. The assets are loaded in this branch only. A visitor who is not logged in gets no editing module, and there is nothing on the page for it to enhance. Both tags are the documented replacement for the HeaderAssets and FooterAssets sections, whose automatic rendering is deprecated since TYPO3 v14.0 (changelog 107057). No inline script is emitted anywhere. There is no link to a login page. No setting names one, and guessing it - the referrer, the current page - would be wrong on some installations. It is added when a setting for it is, together with its label.

The image sits inside the element, unlike in the detail view, because here it is editable. Everything in this element is the no-JavaScript view and is replaced once the element upgrades. Rendering the image outside would leave the served file on screen after a replacement, next to a surface that already shows the new one — the page would disagree with itself about which image the profile has.
